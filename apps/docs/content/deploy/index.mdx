Cloudflare Workers with R2 is the default: deploy the Worker, and you get artifact storage, daily expiry, and a stats database together. It is a good place to start if you do not already have a host in mind.

Already running Node.js, or keeping your infrastructure on AWS? The same server builds for those hosts through Nitro. A long-running server gives you control over memory and proxy limits; managed function platforms handle the process for you but have smaller request limits.

CI runs the Cloudflare deployment end to end with the real Turbo CLI. Other presets serve the same API, but do not have that deployment coverage.

## Hosting requirements

| Platform                                 | Artifact storage                                  | Expiry schedule             | Stats database                                       |
| ---------------------------------------- | ------------------------------------------------- | --------------------------- | ---------------------------------------------------- |
| [Cloudflare Workers](/deploy/cloudflare) | R2 by default; KV, S3, or custom adapter optional | Cloudflare Cron Trigger     | D1 created at deploy                                 |
| [Node.js, Bun, and Deno](/deploy/node)   | S3-compatible bucket or custom adapter            | In the running process      | SQLite by default on Node.js and Deno; configure Bun |
| [Vercel](/deploy/vercel)                 | S3-compatible bucket or custom adapter            | Vercel Cron Job             | Configure a hosted database                          |
| [Netlify](/deploy/netlify)               | S3-compatible bucket or custom adapter            | External scheduler required | Configure a hosted database                          |
| [AWS Lambda](/deploy/aws-lambda)         | S3-compatible bucket or custom adapter            | External scheduler required | Configure a hosted database                          |

[Choose storage](/storage) for backend limits and selection rules. [Retention and expiry](/retention) explains scheduling, and [Configure the stats database](/stats-database) covers database connections.

## Artifact size limits

Check the size of your build artifacts before choosing a host. If an artifact is too large to upload, its task has to run again on the next machine. Your storage backend and any reverse proxy can set lower limits than the host itself.

| Host                   | Request limit                                                                                                                                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Cloudflare Workers     | 100 MB on Free and Pro zones, 200 MB on Business zones. The domain's Cloudflare plan sets the limit, not the Workers billing plan. See [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#request-and-response-limits). |
| Node.js, Bun, and Deno | No server-imposed artifact size cap. Host memory, storage, and any reverse proxy still limit requests.                                                                                                                                           |
| Vercel                 | 4.5 MB request or response body. See [Functions limits](https://vercel.com/docs/functions/limitations#request-body-size).                                                                                                                        |
| Netlify                | About 4.5 MB for binary payloads under the buffered function limit. See [Functions limits](https://docs.netlify.com/build/functions/configuration/).                                                                                             |
| AWS Lambda             | 6 MB synchronous invocation payload, including the event envelope and encoded body. Binary artifacts must be smaller because of Base64 overhead. See [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html).   |

KV has its own 25 MiB limit per artifact. S3 uploads are buffered in memory, which matters especially on Workers. Check your largest build outputs before choosing a host with a small request limit.

## Build from source

For command-line deployments, clone your copy of the repository and install its dependencies first. You need Node.js 24 or later and the pnpm version in `package.json`. Run build commands from the repository root.

Before supplying your server's `TURBO_TOKEN` to a build, remove or replace the root `turbo.json` file's `remoteCache` entry. That entry configures the maintainer's build cache. It is separate from the cache server you are deploying.

`NITRO_PRESET` chooses the build target:

| Platform           | Preset                           |
| ------------------ | -------------------------------- |
| Cloudflare Workers | `cloudflare_module`, the default |
| Node.js            | `node_server`                    |
| Bun                | `bun`                            |
| Deno               | `deno_server`                    |
| Vercel             | `vercel`, detected on Vercel     |
| Netlify            | `netlify`, detected on Netlify   |
| AWS Lambda         | `aws_lambda`                     |

For example:

```sh
NITRO_PRESET=node_server pnpm build
```

Keep local deployment changes in your copy and [update from upstream releases](/update).
