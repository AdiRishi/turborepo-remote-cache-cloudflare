Cloudflare Workers is the flagship deployment target. It provisions R2 artifact storage, D1 dashboard analytics, and daily cron expiry out of the box with zero egress fees on R2.

<a id="before-you-begin" />

## Prerequisites

1. **Activate R2** in the [Cloudflare dashboard](https://dash.cloudflare.com/) under **R2 Object Storage** if your account hasn't enabled it yet (includes 10 GB/month free on the [R2 free tier](https://developers.cloudflare.com/r2/pricing/)).
2. **Generate a bearer token** to share between your Worker and `turbo` clients:

    ```sh
    openssl rand -hex 32
    ```

    Remember that one token grants read/write access across all teams on this deployment. See [Security model and trade-offs](/introduction#one-token-opens-every-team).

:::tip[Pin your R2 bucket region]
On first deploy, Cloudflare creates the R2 bucket near the runner executing the deployment. If you want the bucket pinned near your CI fleet, [create it with a location hint before deploying](/storage/r2#choose-where-the-bucket-lives).
:::

## One-click deploy

<a href="https://deploy.workers.cloudflare.com/?url=https://github.com/AdiRishi/turborepo-remote-cache">
    <img
        src="https://deploy.workers.cloudflare.com/button"
        alt="Deploy to Cloudflare"
        width="184"
        height="39"
    />
</a>

<Steps>
    <Step title="Fork and deploy via Workers Builds">
        Click **Deploy to Cloudflare**, sign in, and connect your GitHub or GitLab account. Cloudflare forks this repository into your account and wires up [Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/).

        Keep the default build command (`pnpm run build`) and deploy command (`pnpm run deploy`). Both must run from the repository root so workspace packages build first.
    </Step>
    <Step title="Wait for provisioning">
        The initial deploy creates three resources automatically:

        - Worker: `turborepo-remote-cache`
        - R2 bucket: `turborepo-cache`
        - D1 database: `turborepo-cache-stats` (for the [dashboard](/dashboard))
    </Step>
    <Step title="Add TURBO_TOKEN">
        In the Cloudflare dashboard, open **Workers & Pages** > **turborepo-remote-cache** > **Settings** > **Variables and Secrets**, and add a secret named `TURBO_TOKEN` with your generated token.

        Copy your Worker's URL (e.g. `https://turborepo-remote-cache.<your-subdomain>.workers.dev`).
    </Step>

</Steps>

:::note
Until `TURBO_TOKEN` is configured, authenticated endpoints intentionally return `500` rather than running unsecured.
:::

## Deploy with Wrangler CLI

Requires [Node.js](https://nodejs.org) 24+ and the [pnpm](https://pnpm.io/installation) version listed in `package.json`.

<Steps>
    <Step title="Clone and install">
        ```sh
        git clone https://github.com/AdiRishi/turborepo-remote-cache.git
        cd turborepo-remote-cache
        pnpm install
        ```
    </Step>
    <Step title="Clean up root turbo.json">
        Remove `remoteCache` from the repository's root `turbo.json` (or point it at your own deployment) so `turbo` doesn't send your local `TURBO_TOKEN` to the maintainer's cache while building.
    </Step>
    <Step title="Build and deploy">
        ```sh
        pnpm build
        pnpm run deploy
        ```

        Wrangler prompts you to authenticate with Cloudflare if needed, provisions `turborepo-cache` (R2) and `turborepo-cache-stats` (D1) on first run, and prints the live Worker URL.
    </Step>
    <Step title="Set TURBO_TOKEN">
        ```sh
        cd apps/api
        pnpm exec wrangler secret put TURBO_TOKEN
        ```

        Paste your generated token when prompted.
    </Step>

</Steps>

## Check the deployment

Verify both the unauthenticated health check and authenticated status endpoint:

```sh
CACHE_URL='https://turborepo-remote-cache.<your-subdomain>.workers.dev'
export TURBO_TOKEN='<your-token>'

curl --fail-with-body "$CACHE_URL/ping"
curl --fail-with-body -H "Authorization: Bearer $TURBO_TOKEN" "$CACHE_URL/v8/artifacts/status"
```

`/ping` should return `pong`, and `/v8/artifacts/status` should return `{"status":"enabled"}`. A `401` indicates a token mismatch; for anything else, see [`turbo` cannot connect](/troubleshooting#turbo-cannot-connect).

Once verified, follow [Connect Turborepo](/connect-turbo) to hook up your monorepo and confirm remote cache hits.

## Continuous deployment

Choose **either** Workers Builds or GitHub Actions to deploy pushes from your fork. Enabling both will deploy every commit twice.

### Workers Builds

Already configured if you used the one-click deploy button. Keep the build root at `/`, build command at `pnpm run build`, and deploy command at `pnpm run deploy`.

### GitHub Actions

The included [CI workflow](https://github.com/AdiRishi/turborepo-remote-cache/blob/master/.github/workflows/ci.yml) deploys pushes to `master` after checks and end-to-end tests pass. To adapt it for your fork:

1. Remove the `release`, `docs-cloudflare`, and `docs-preview-cleanup` jobs (those publish upstream releases and this documentation site).
2. Add three secrets under **Settings** > **Secrets and variables** > **Actions**:
    - `CLOUDFLARE_API_TOKEN`: API token with edit permissions for Workers, R2, and D1.
    - `CLOUDFLARE_ACCOUNT_ID`: Your Cloudflare account ID.
    - `TURBO_TOKEN`: Synced to your Worker secret on each deploy. Don't omit this; the workflow falls back to a placeholder (`SECRET`) if unset.
3. Remove or update `remoteCache` in the root `turbo.json` so CI doesn't transmit your `TURBO_TOKEN` to the upstream cache.
4. Push to `master`. If your production branch has a different name (such as `main`), update both the workflow's branch filters and the `deploy` job's `if` condition (`refs/heads/master`).

To pull new upstream releases into your fork later, see [Updating your deployment](/update).
