On Cloudflare Workers, `apps/api/wrangler.jsonc` enables [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/), [Workers Traces](https://developers.cloudflare.com/workers/observability/traces/), and [Issues](https://developers.cloudflare.com/workers/observability/issues/) out of the box, along with uploaded source maps so stack traces resolve to exact TypeScript lines in `apps/api/src`.

## What gets recorded on Cloudflare

| Signal     | Details                                                                                                                                                              |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Logs**   | One entry per request (method, URL, status), full stack traces on `500` errors, and `[stats]` error entries when an async dashboard DB write fails.                  |
| **Traces** | End-to-end request trace with automatic Cloudflare spans for R2, KV, and D1 operations alongside sibling route/middleware spans (such as `GET /v8/artifacts/:hash`). |
| **Issues** | Grouped uncaught exceptions, `5xx` responses, and error logs, including background `[stats]` failures even when the underlying cache request succeeded.              |

## Configure sampling

`turbo` makes at least one HTTP request per task, producing one log event and roughly six trace spans per request. Starting December 1, 2026, Cloudflare meters logs and traces under [Cloudflare Observability pricing](https://developers.cloudflare.com/workers/observability/logs/workers-logs/#pricing).

Use `head_sampling_rate` (between `0` and `1`) in `apps/api/wrangler.jsonc` to sample whole requests. For example, to keep 10% of logs and 5% of traces:

```jsonc apps/api/wrangler.jsonc
{
    "observability": {
        "enabled": true,
        "logs": { "head_sampling_rate": 0.1 },
        "traces": { "enabled": true, "head_sampling_rate": 0.05 },
        "issues": { "enabled": true },
    },
}
```

Set `enabled: false` on any signal you want to turn off completely, then redeploy.

## Export via OpenTelemetry

Cloudflare can stream logs and traces over OpenTelemetry to Honeycomb, Grafana Cloud, Axiom, Sentry, and other OTLP backends. Create a destination in the Cloudflare dashboard (see [Export OpenTelemetry data](https://developers.cloudflare.com/workers/observability/exporting-opentelemetry-data/)), then reference its name in `apps/api/wrangler.jsonc`:

```jsonc apps/api/wrangler.jsonc
{
    "observability": {
        "enabled": true,
        "logs": { "destinations": ["honeycomb-logs"] },
        "traces": { "enabled": true, "destinations": ["honeycomb-traces"] },
        "issues": { "enabled": true },
    },
}
```

Add `"persist": false` under `logs` or `traces` if you want to forward telemetry without storing a copy in Cloudflare.

## Other platforms

On Node.js, Bun, Deno, Vercel, Netlify, and AWS Lambda, error logs and `[stats]` failures write to `stderr` so your host's log collector captures them automatically.

The server also emits standard Node.js [`diagnostics_channel` tracing channels](https://nodejs.org/api/diagnostics_channel.html#class-tracingchannel) wherever supported:

| Channel        | Scope                                                                  |
| -------------- | ---------------------------------------------------------------------- |
| `srvx.request` | Full HTTP request/response lifecycle on standalone server runtimes.    |
| `h3.request`   | Individual route and middleware handlers (e.g. `/v8/artifacts/:hash`). |
| `db0.query`    | Queries against the stats database.                                    |

On Vercel, Nitro automatically attaches these spans to [Vercel Traces](https://vercel.com/docs/tracing). On Node.js, Bun, or Deno, APM agents or custom subscribers can consume them directly. For example, to emit structured JSON access logs:

```js access-log.mjs
import { subscribe } from 'node:diagnostics_channel';

subscribe('tracing:srvx.request:asyncEnd', ({ request, result }) => {
    console.log(
        JSON.stringify({
            method: request.method,
            url: request.url,
            status: result.status,
        }),
    );
});
```

Preload the subscriber with source maps enabled:

```sh
cd apps/api
node --enable-source-maps --import ./access-log.mjs .output/server/index.mjs
```

During local development, set `experimental: { tracingLogger: true }` in `apps/api/nitro.config.ts` to print per-request span timelines to the terminal.
