title: Troubleshooting
description: Diagnose connection failures, persistent cache misses, failed uploads, 500 errors, and missing dashboard analytics.
---

Because `turbo` falls back silently to local execution whenever remote caching fails, a passing build doesn't prove your remote cache was used. Match your symptom below. Commands assume `CACHE_URL` holds your server origin and `TURBO_TOKEN` holds your bearer token.

## `turbo` cannot connect

If `turbo` prints a warning instead of `Remote caching enabled`, check the message first:

| Turborepo message                                                                | Likely cause                                            |
| -------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `Remote caching disabled (TURBO_TOKEN set without TURBO_TEAM)`                   | No team slug or team ID is configured.                  |
| `Remote caching unavailable (Authentication failed ...)`                         | Client `TURBO_TOKEN` doesn't match the server's secret. |
| `Remote caching unavailable (Could not connect to "https://cache.example.com/")` | Wrong URL or trailing slash in `apiUrl` / `TURBO_API`.  |

Test reachability and authentication directly:

```sh
curl --fail-with-body "$CACHE_URL/ping"
curl --fail-with-body -H "Authorization: Bearer $TURBO_TOKEN" "$CACHE_URL/v8/artifacts/status"
```

Expect `pong` followed by `{"status":"enabled"}`.

| Result                                        | What to check                                                                                                                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DNS, TLS, or connection error                 | Confirm the deployment URL is reachable and uses the bare HTTPS origin (no trailing slash, no `/v8`).                                                     |
| HTML response or login redirect               | Deployment protection or an access proxy (Cloudflare Access, Vercel Protection) is blocking `/v8/*`. Allow bearer-authenticated requests through `/v8/*`. |
| `401`                                         | `TURBO_TOKEN` is missing or doesn't match the server's `TURBO_TOKEN`.                                                                                     |
| `500`                                         | Check server logs. See [The server returns 500](#the-server-returns-500).                                                                                 |
| `curl` succeeds, but `turbo` disables caching | Verify `teamSlug` / `TURBO_TEAM` is set and check for stale `TURBO_*` environment variables overriding `turbo.json`.                                      |

`/ping` only confirms the process is running; run the [remote-hit check](/connect-turbo#check-that-hits-come-from-the-server) to validate the full upload/download path.

## Builds keep missing

1. **Verify artifacts were actually uploaded.** `turbo` only uploads tasks it executes; local cache hits are never uploaded. If you built before connecting the server, clear `.turbo/cache` and rebuild once (see the [remote-hit check](/connect-turbo#check-that-hits-come-from-the-server)).
2. **Inspect cache provenance.** Run `npm exec -- turbo run build --summarize` and open the JSON file under `.turbo/runs/`. Each task's `cache.source` is `LOCAL`, `REMOTE`, or absent on a miss.
3. **Compare task hashes across machines.** If two machines generate different hashes for the same commit, `turbo` sees different inputs (often differing env vars, line endings, or OS). See [Turborepo's caching troubleshooting guide](https://turborepo.dev/docs/crafting-your-repository/caching#troubleshooting).
4. **Confirm matching URL and team.** Different `teamSlug` / `teamId` values isolate artifacts under separate prefixes.
5. **Check for silent upload errors.** A task can pass locally while its `PUT` fails. See [Uploads fail](#uploads-fail).
6. **Check signing keys.** If `remoteCache.signature` is enabled, every machine must share the exact same `TURBO_REMOTE_CACHE_SIGNATURE_KEY`. An invalid signature is treated as a miss ([Artifact signing](/sign-artifacts)).

Note that switching storage backends or passing the retention window causes one-time misses as the cache warms up again. On Workers KV, newly uploaded artifacts can take 60+ seconds to replicate across regions.

On a new S3-compatible store where every read misses, verify endpoint, bucket name, IAM permissions, and whether your provider requires `S3_FORCE_PATH_STYLE=true` ([S3-compatible storage](/storage/s3)).

## Uploads fail

Inspect the HTTP status and server [logs](/observability):

- **`413 Payload Too Large`:** The artifact exceeded the host's or proxy's request size cap. Compare your artifact size against [Artifact size limits](/deploy#artifact-size-limits).
- **Cloudflare KV `400`:** KV caps individual values at 25 MiB. Switch to R2 or an S3-compatible bucket for larger outputs.
- **S3 out-of-memory errors:** The S3 adapter buffers uploads in memory before writing; large artifacts can exceed container or Worker memory limits even below the HTTP body cap.
- **Custom adapter rejections:** The adapter must support custom user metadata (`x-artifact-duration`, `x-artifact-tag`).

Also confirm storage credentials have read, write, list, and delete permissions (list and delete are required for expiry and storage metrics).

## The server returns 500

Search your platform logs for `Invalid server configuration:`. The server intentionally hides configuration details from HTTP responses and logs the exact cause (missing `TURBO_TOKEN`, invalid `BUCKET_OBJECT_EXPIRATION_HOURS`, or missing storage backend).

Cross-check [Server configuration](/configuration) and [backend resolution order](/storage#how-the-server-picks-a-backend). Remember that Cloudflare `KV_STORE` and `R2_STORE` bindings override `S3_*` variables; setting S3 env vars alone won't switch a Worker away from R2.

If configuration is valid, inspect the stack trace and upstream storage error in your logs.

## Dashboard stats are unavailable

Query the stats endpoint directly:

```sh
curl --fail-with-body "$CACHE_URL/stats"
```

If the JSON contains `"enabled": false`, the server couldn't connect to a stats database. Search logs for `[stats]` errors and review [Stats database](/stats-database). On Node.js and Deno, ensure `.data/db.sqlite` lives on persistent storage; on serverless hosts, configure a hosted database and rebuild after editing `apps/api/nitro.config.ts`.

## Storage figures are empty or stale

Storage metrics are collected during the daily expiry sweep, not on every upload. [Trigger expiry on demand](/retention#run-expiry-on-demand) and refresh the dashboard to populate them immediately. On Netlify and AWS Lambda, configure an [external scheduler](/retention#run-expiry-from-a-scheduler) so metrics stay current.

## Expiry returns 400

`POST /internal/delete-expired-objects` requires a JSON body with `Content-Type: application/json`, even when using the default retention window. Pass `-d '{}'` as shown in [Run expiry on demand](/retention#run-expiry-on-demand).

## Reporting a bug

Open an issue on [GitHub Issues](https://github.com/AdiRishi/turborepo-remote-cache/issues) with your server version or commit SHA, `turbo` version, hosting platform, storage backend, failing command/status code, and redacted logs. For security vulnerabilities, follow the [security policy](https://github.com/AdiRishi/turborepo-remote-cache/security/policy).
