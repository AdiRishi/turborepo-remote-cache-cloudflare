Turborepo Remote Cache is an open-source, self-hosted implementation of the [Turborepo Remote Cache v8 API](https://turborepo.dev/docs/core-concepts/remote-caching#remote-cache-api). Deploy it into your own Cloudflare account in a click, or build it for Node.js, Bun, Deno, Vercel, Netlify, or AWS Lambda, to share build artifacts across every machine running `turbo`.

<CacheFlow />

## Why teams run a remote cache

Local caching only helps the machine that ran the build. A remote cache shares task outputs across everyone and everything touching your monorepo:

- **Faster CI pipelines.** Pull requests only rebuild affected packages and their dependents; unchanged tasks download and replay in milliseconds.
- **Instant onboarding and worktrees.** Fresh clones, new laptops, and ephemeral git worktrees pull warm artifacts instead of compiling from scratch.
- **Faster coding-agent loops.** Agents iterating on tests and typechecks across branches replay every untouched task instead of re-executing the workspace.

<a id="how-turbo-uses-the-cache" />

## How a build flows

`turbo` hashes the inputs of each task (files, environment variables, dependencies, and configuration) and checks the remote cache before executing anything:

1. **Lookup:** `turbo` queries `HEAD` or `GET /v8/artifacts/:hash` with your team identifier and bearer token.
2. **Cache hit:** The server streams the archived output and metadata headers back. `turbo` restores the files, replays the terminal logs, and skips execution.
3. **Cache miss:** `turbo` executes the task, packs its outputs, and uploads the archive via `PUT /v8/artifacts/:hash`. Every subsequent machine with the same inputs hits the cache.

<a id="what-the-server-stores" />

The server stores each artifact under `<team>/<hash>`, where `<team>` comes from the `teamId` or `slug` query parameter (falling back to `team_default_team` if omitted). Alongside the payload, it preserves headers uploaded by `turbo`, including task duration (`x-artifact-duration`) and artifact signatures (`x-artifact-tag`).

Artifacts expire after 30 days by default via a daily cleanup task. See [Retention and expiry](/retention) to adjust the TTL or schedule.

## Architecture

- **Server ([Nitro](https://nitro.build)):** Compiles the same H3 application to Cloudflare Workers (`cloudflare_module`, the default and end-to-end tested build) as well as Node.js, Bun, Deno, Vercel, Netlify, and AWS Lambda.
- **Storage ([Files SDK](https://files-sdk.dev)):** Abstracts artifact storage across Cloudflare R2, Workers KV, any S3-compatible bucket, or a [custom adapter](/storage/custom-adapter).
- **Analytics ([Dashboard](/dashboard)):** Served at `/` with a JSON endpoint at `/stats`. Usage records are written asynchronously after each HTTP response so database latency or outages never slow down or fail a build.

## Security model and trade-offs

Keep these security boundaries and trade-offs in mind before deploying to production:

<a id="one-token-opens-every-team" />
<a id="your-copy-is-yours-to-update" />

- **One shared bearer token across teams.** All `/v8/*` and `/internal/*` endpoints authenticate against `TURBO_TOKEN` using constant-time SHA-256 comparison. Teams separate artifact namespaces, not permissions: anyone with `TURBO_TOKEN` can read and write artifacts for any team. If two groups must be isolated, run separate deployments.
- **Client-side integrity via signing.** Enable [artifact signing](/sign-artifacts) on any shared cache. `turbo` signs uploads and verifies downloads locally using HMAC-SHA256; the server never sees the signing key, so a compromised bearer token cannot poison builds.
- **Public dashboard by default.** `/` and `/stats` require no authentication and expose team names and usage statistics. Put both routes behind [Cloudflare Access or a reverse proxy](/dashboard#restrict-access) before sharing the URL.
- **Self-managed updates.** Deploying forks this repository into your account. Your deployment won't auto-update; pull upstream releases when ready by [merging tagged versions](/update).
- **Serverless payload limits.** Vercel, Netlify, and AWS Lambda cap request bodies at roughly 4.5–6 MB. Cloudflare Workers accepts 100 MB+ (and long-running Node.js, Bun, or Deno servers have no built-in cap). Check [platform limits](/deploy#artifact-size-limits) if your monorepo produces large build outputs.
