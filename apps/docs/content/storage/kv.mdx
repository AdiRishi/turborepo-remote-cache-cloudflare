On Cloudflare Workers, you can store artifacts in a Workers KV namespace bound as `KV_STORE`. Each artifact is stored as a KV value, with its byte length, upload timestamp, and `turbo` headers stored in KV metadata.

## Limitations to check first

- **25 MiB hard ceiling:** KV rejects values over 25 MiB. The server returns `400` on larger uploads, so oversized tasks will never cache remotely.
- **Eventual consistency:** Newly written artifacts are immediately readable in the edge region that wrote them, but propagation to other regions can take 60 seconds or more.

For most monorepos, [Cloudflare R2](/storage/r2) is a better fit.

## Bind a KV namespace

<Steps>
    <Step title="Add the KV_STORE binding">
        Add `kv_namespaces` to `apps/api/wrangler.jsonc`:

        ```jsonc apps/api/wrangler.jsonc
        {
            "kv_namespaces": [{ "binding": "KV_STORE" }],
        }
        ```

        Omitting `id` lets `wrangler deploy` create and bind a new namespace automatically. To reuse an existing namespace, include its `id`.
    </Step>
    <Step title="Remove the R2 binding (optional)">
        When both `KV_STORE` and `R2_STORE` are bound, `KV_STORE` wins automatically. Remove `r2_buckets` from `wrangler.jsonc` if you no longer need the unused R2 binding.
    </Step>
    <Step title="Rebuild and deploy">
        ```sh
        pnpm build
        pnpm run deploy
        ```
    </Step>

</Steps>

## How entries expire

Every KV write attaches an `expirationTtl` matching `BUCKET_OBJECT_EXPIRATION_HOURS`, so Cloudflare expires entries automatically. The daily `cache:delete-expired` task also runs against the current `BUCKET_OBJECT_EXPIRATION_HOURS` setting and removes any entry older than that threshold.

KV locks an entry's native `expirationTtl` at write time, so raising `BUCKET_OBJECT_EXPIRATION_HOURS` does not extend previously written entries. Lowering `BUCKET_OBJECT_EXPIRATION_HOURS`, however, causes the next daily cleanup sweep to delete existing entries older than the new limit unless scheduled expiry is disabled.

Upgrading an existing KV cache from v4? Read [Upgrading from v4](/upgrade-from-v4#stored-artifacts) for how v4 metadata is handled.
